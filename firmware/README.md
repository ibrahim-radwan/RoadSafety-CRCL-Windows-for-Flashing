# AM273x cascade firmware: source, build and releases

This folder is the **single source of truth** for the AWR2243-2X cascade firmware that runs on the AM273x MSS. Every image deployed to the Jetson is built from here and recorded under `releases/`.

| Path | What it is |
|---|---|
| `am273x_cascade/` | Firmware source: chirp parameters (`am273x/cascade_config.h`), MSS application, linker and SysConfig outputs, makefiles |
| `am273x_cascade/tools/` | Build, packaging and verification tools |
| `releases/2026-10-10_v2/` | The firmware tree deployed to the Jetson on 2026-10-10: 20 variants, `firmware_map.json`, flash configs and build records. `2026-10-10_v2.MANIFEST.txt` holds the md5 of every file. |
| `archive/cascade_enet_experiment_2026-03/` | Source-only snapshot of the March 2026 Ethernet-streaming experiment. Not built, not deployed. |

The full story behind the current images (stale-data defect, fix, verification) is in `testing/firmware_investigation_2026-10/`. Start with its `README.md`.

## 1. How the source reaches the TI SDK (junction)

The cascade makefile includes `../../../common/mmwave_sdk.mak`, so it only builds from inside the SDK at `<SDK>\ti\utils\test\<name>\`. Rather than keep a second copy of the source there, the SDK holds a **directory junction** that points back at this repo:

```
C:\ti\mmwave_mcuplus_sdk_04_04_00_01\mmwave_mcuplus_sdk_04_04_00_01\ti\utils\test\cascade_radar
    -> <repo>\firmware\am273x_cascade
```

One copy of the source exists, and edits from either path are the same file. Build outputs (`obj_am273x\`, `am273x\build_*_inf\`, `*.xer5f`, `*.map`) land in `am273x_cascade\` and are ignored by `.gitignore`.

Create the junction once per machine (no admin rights needed):

```powershell
powershell -ExecutionPolicy Bypass -File firmware\am273x_cascade\tools\setup_sdk_junction.ps1
```

**Verified 2026-10-12:** all 13 v2 images, built from this repo through the junction, reproduce the deployed `.rprc` and `.appimage` md5s exactly.

The four folders that used to live in the SDK (`cascade`, `cascade - Copy`, `cascade - Copy (2)`, `cascade - Copy (3)`) were moved to `C:\ti\_archive_cascade_sdk_folders_20261012\`. `cascade - Copy` is the folder this source was taken from. Nothing builds from the archive.

## 3. Variants

A variant is a `CASCADE_CFG_*` define that selects one block in `am273x/cascade_config.h`.

- **Base blocks:** `SHORTRANGE` (r017m), `SHORTRANGE_CALIB` (r017m_calib), `R050M`, `R075M`, `R100M`, `VERYLONGRANGE` (r142m), `LONGRANGE` (r168m).
- **`_V2` family:** each `CASCADE_CFG_<V>_V2[_8FPS]` define selects its base block unchanged, then overrides only:
  - HPF1/HPF2 → 0/0 (175 kHz / 350 kHz);
  - for `_8FPS`, the frame period → 125 ms.

  `R075M_V2` and `R075M_V2_8FPS` keep their own explicit block. `r017m_calib_v2` keeps 1000 ms.
- **Every image built from this source** carries the DSS L3 MEMINIT fix in `am273x/main_mss.c`. Without it, a QSPI-booted image streams ~50% stale words per chirp. See the investigation.

| Short name | Define | Max range | Window at HPF 0/0 | Periods built |
|---|---|---|---|---|
| r017m_v2 | `CASCADE_CFG_R017M_V2[_8FPS]` | 16.78 m | 1.17 – 16.78 m | 250 / 125 ms |
| r017m_calib_v2 | `CASCADE_CFG_R017M_CALIB_V2` | 16.78 m | 1.17 – 16.78 m | 1000 ms |
| r050m_v2 | `CASCADE_CFG_R050M_V2[_8FPS]` | 50.00 m | 1.75 – 50.00 m | 250 / 125 ms |
| r075m_v2 | `CASCADE_CFG_R075M_V2[_8FPS]` | 74.99 m | 2.62 – 74.99 m | 250 / 125 ms |
| r100m_v2 | `CASCADE_CFG_R100M_V2[_8FPS]` | 100.15 m | 3.51 – 100.15 m | 250 / 125 ms |
| r142m_v2 | `CASCADE_CFG_R142M_V2[_8FPS]` | 142.42 m | 9.97 – 142.42 m | 250 / 125 ms |
| r168m_v2 | `CASCADE_CFG_R168M_V2[_8FPS]` | 167.82 m | 5.87 – 167.82 m | 250 / 125 ms |

The old base images (r017m … r168m without `_v2`) remain in the release only so that old recordings can still be attributed. Their `data_valid` field in `firmware_map.json` says they are not valid when booted from QSPI. Do not flash them.

## 4. Building and packaging

**Build + package one or more variants** (compile, then `elf2rprc`, then `multicoreImageGen --devID 55`, straight into a Jetson-layout tree):

```powershell
cd firmware\am273x_cascade\tools
.\build_v2_variants.ps1 -Out C:\temp\fw_out -Variants 'r050m_v2=CASCADE_CFG_R050M_V2','r050m_v2_8fps=CASCADE_CFG_R050M_V2_8FPS'
```

Output per variant:

- `<Out>\<v>\am273x_cascade_<v>.appimage`
- `<Out>\_build_record\<v>\{<v>.rprc, <v>.xer5f, am273x_cascade_mss.map}`

The script names every intermediate after its variant, so the old shared-`am273x_cascade_mss.rprc` overwrite hazard cannot occur.

**Other entry points:**

- `am273x_cascade\build_one_inf.bat <DEFINE>` compiles one variant into `am273x\am273x_cascade_mss.xer5f`.
- `am273x_cascade\build_inf_custom.bat` runs `gmake mssTestInf`, which builds every variant into `am273x\build_*_inf\`.

**Identity rules** (see `docs/BUILD_DETERMINISM_FINDING.md`):

- **Never** use the `.xer5f` hash: the linker output is non-deterministic.
- The **`.rprc`** md5 is the reproducible fingerprint of the compiled parameters.
- The **`.appimage`** md5 identifies what is written to QSPI.

**Adding a new variant:**

1. Add a block or `_V2` mapping in `cascade_config.h`, and its line in the `makefile` `mssTestInf` target.
2. Build with `build_v2_variants.ps1` into a copy of the current release tree.
3. Generate the map entries, `.cfg` and flash configs with `tools\gen_v2_release_metadata.py <tree>`, after copying its `NEW` list pattern.
4. Verify:
   - `python fill_firmware_map.py --root <tree>`: every column `ok` except `flash`, which only resolves on the Jetson;
   - `tools\fdiff.py <base.xer5f> <new.xer5f>`: only the intended immediates differ;
   - both Jetson `.cfg` parsers.
5. Write a new `MANIFEST.txt` and add the tree as a new folder under `releases/`.

## 5. Release `2026-10-10_v2`

- **What it is:** a drop-in copy of the Jetson's `cascaded_radar_capture_pipeline/firmware/`.
- **Contents:** 20 variants (7 old base images kept for attribution, 13 v2 images), `firmware_map.json`, `flash_provision.cfg`, `fill_firmware_map.py` and `make_flash_cfgs.py`.
- **Flash configs** carry absolute Jetson paths and write only the application slot `0xA0000`.
- **Status:** deployed to the Jetson 2026-10-12. Hardware-confirmed on r075m_v2 / r075m_v2_8fps (0.00% stale words, holding across power cycles).
- **Hashes:** per-variant md5s are in `firmware_map.json` and `testing/firmware_investigation_2026-10/rebuild_all_variants/REBUILD_SUMMARY.md`.
- **Flashing:** done on the Jetson only, with `flashing/boot/flash_variant.sh <variant> <port>` in conda env `rel_1_py_3_8`. See `testing/firmware_investigation_2026-10/investigation/FLASH_PROCEDURE.md`.

**Capture requirement:** at 8 fps the DCA1000 packet delay must be **25 µs** (3125 ticks). 50 µs takes 134 ms per frame and silently loses data (`firmware_map.json` `conventions.dca_wire_time`).
